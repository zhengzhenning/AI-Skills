# 编码规范

## 目标与设计思路

把“风格偏好”转化为可判断、可自动化、可持续执行的工程约束。规范必须服务于可读性、正确性、可维护性和安全性，而不是追求格式统一本身。

采用三层设计：

1. **项目层**：优先遵守 `AGENTS.md`、贡献指南、构建配置、已有 lint/formatter 和相邻代码的稳定惯例。
2. **语言层**：只补充当前语言和框架的通用最佳实践，避免与项目事实冲突。
3. **执行层**：每条规则都绑定检查方式、例外条件和修复建议；能自动化的交给工具，不能自动化的进入评审清单。

## 触发后的工作流

1. **确定任务类型**：区分“制定规范”“审查代码”“修复违规”“配置门禁”。明确范围、语言、模块和是否允许修改文件。
2. **收集事实**：读取仓库级指令、构建/依赖配置、格式化和静态检查配置、CI 脚本、测试约定，以及目标文件和相邻实现。不得把猜测写成项目规则。
3. **建立规则表**：为每条规则记录类别、适用范围、严重级别（阻断/应修复/建议）、违反示例、验证命令和例外条件。详细模板见 [references/rule-catalog.md](references/rule-catalog.md)。
4. **按风险审查**：先查正确性、安全、并发、资源和错误处理，再查 API/分层、可维护性、可读性，最后查格式和命名。发现一处根因后，检查同类问题是否成片存在。
5. **提出变更**：只修改用户授权范围内的文件；优先使用已有 formatter/linter 配置，不引入仅为“看起来统一”的新工具。大规模迁移先给出影响面和分批策略。
6. **验证交付**：运行与改动匹配的格式检查、静态检查、单元测试和构建；记录实际命令及结果。无法运行时说明原因和剩余风险。

## 审查与输出要求

- 结论必须引用文件和行号，先列问题再给摘要；按严重级别排序，避免只给泛泛建议。
- 每个问题说明：现象、风险、建议修复、验证方式；不把纯风格偏好伪装成缺陷。
- 规范文档使用“必须/禁止/应该/可以”等明确措辞，并给出最小正例和反例。
- 项目现有规则与通用建议冲突时，以项目规则为准，并指出冲突来源。
- 例外必须有边界和理由，例如性能热点、生成代码、第三方协议字段或兼容性要求。
- 不为一次性问题创建抽象；不在无关文件中顺手格式化或重命名。

## 规则分类

至少覆盖以下类别，并按任务需要裁剪：命名与目录、格式与注释、类型与 API、错误处理、日志与敏感信息、并发与资源生命周期、分层与依赖、测试、性能、可观测性和工具门禁。跨语言差异和示例按需读取 [references/language-adaptation.md](references/language-adaptation.md)。

## 完成检查

- [ ] 已读取并遵守仓库级指令与现有工具配置。
- [ ] 规则有明确范围、优先级、例外和验证方式。
- [ ] 审查结论区分事实、推断和待确认项。
- [ ] 关键风险（安全、正确性、并发、资源、错误处理）已优先检查。
- [ ] 已运行可用的格式、静态检查、测试或构建，并如实报告结果。
- [ ] 规范变更有迁移顺序，避免一次性制造不可审查的大 diff。
