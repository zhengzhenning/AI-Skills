# 规则目录与记录模板

## 规则记录

每条规则按以下字段记录，便于转成 lint 规则或评审检查项：

| 字段 | 要求 |
| --- | --- |
| ID | 稳定、唯一，例如 `ERR-001` |
| 类别 | 命名、API、错误处理、安全、测试等 |
| 规范 | 使用必须/禁止/应该/可以，避免模糊词 |
| 范围 | 语言、目录、文件类型或调用场景 |
| 级别 | 阻断、应修复、建议 |
| 正例/反例 | 最小、可直接对比 |
| 自动化 | formatter、linter、编译器、测试或人工评审 |
| 例外 | 触发条件、审批人或记录位置 |

## 最小规则集

### 正确性与安全

- 外部输入必须在边界处校验，禁止把未验证数据直接拼接进查询、命令、路径或 HTML。
- 错误不得静默吞掉；必须保留上下文并在边界处转换为稳定的错误契约。
- 日志禁止记录令牌、密码、完整身份证件、支付数据等敏感信息；链路字段和业务主键按项目约定保留。
- 资源（连接、文件、锁、协程/线程）必须有明确的获得、使用、释放路径；异常路径与取消路径同样处理。

### 结构与可维护性

- 一个函数/类只承担可解释的单一职责；跨层调用通过明确契约完成，禁止绕过边界直接修改他方数据。
- 公共 API 的命名、参数、返回值和兼容策略必须与现有约定一致；破坏性变更需说明迁移方案。
- 重复逻辑只有在语义、变化原因和生命周期一致时才抽象；否则保留局部实现并注明差异。

### 测试与门禁

- 新增行为必须有与风险匹配的测试；边界、失败、权限和并发场景不能只测成功路径。
- 规范对应的自动检查必须固定在开发命令或 CI 中，并记录版本、命令和失败处理方式。
