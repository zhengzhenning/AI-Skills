# 测试计划文档编写

## 核心目标

测试计划只保留三类信息：

1. 场景覆盖矩阵：业务元素与场景类型的选取结果及未选原因。
2. 可执行的测试用例。
3. 用例执行后的实际返回结果与测试结果。

删除项目背景、排期、环境说明、角色职责、缺陷流程、发布门禁、泛化测试策略等与单条用例执行和判定无直接关系的内容。最多保留一行标题或版本范围用于定位。

## 触发边界

- 只有用户明确写出 `$test-plan-writing` 时使用本技能。
- 用户只说“写测试计划”“整理测试用例”“复审用例”但未指定本技能时，不使用。
- 未被显式指定时，不以任何形式引用、加载或执行本技能内容。

## 文档分组

测试用例不得平铺，文档按以下顺序组织二级章节：

1. `## 场景覆盖矩阵`：填写业务元素与场景类型的选取结果及未选原因。
2. `## 灰度环境`：只放验证灰度目标用户、流量、标签、版本或开关的用例。
3. `## 非灰度环境`：只放验证非灰度用户、全量版本或默认开关的用例。

开始编写文档前，必须先向用户确认两个环境各自的测试分支（或工作树）：灰度环境测试分支、非灰度环境测试分支。两者均确认后再生成对应章节；任一分支未提供或无法核实时，先暂停生成并提出确认，不得猜测或用同一个分支代替两个环境。同时按「结合业务选择场景类型」完成业务元素识别与必选类型映射，识别不确定的业务元素一次性向用户确认，不得默认不存在而跳过。

场景覆盖矩阵使用表格，列固定为 `业务元素`、`已覆盖场景类型（用例编号）`、`未覆盖类型及原因`：

```markdown
| 业务元素 | 已覆盖场景类型（用例编号） | 未覆盖类型及原因 |
| --- | --- | --- |
| HTTP 接口 POST /api/login | 正常（TC-GRAY-001）、异常（TC-GRAY-002） | 时间与时钟：接口无时间语义 |
```

同一业务场景在两个环境的预期行为可能不同（灰度命中、开关、版本差异）时，在两个章节各写一条独立用例；与灰度命中无关的行为（如事务与一致性、依赖故障的功能表现）默认只在灰度环境章节写一条，并在矩阵的“已覆盖场景类型”中注明“仅灰度”。章节已经表达环境类型，不再在每条用例中重复“验证模式”字段。映射后两环境预计合计超过 20 条用例时，先向用户提出按类型分优先级（正常、异常优先），确认后再成文。

每个环境章节标题后必须紧跟环境归属信息，并按三项列表展示，避免把多项信息拼成一行：

```markdown
- 环境归属：<灰度/非灰度>
- 测试分支/工作树：<实际分支名或工作树路径>
- 归属基线：<远程基线分支，例如 origin/main>
```

- `测试分支/工作树`必须填写执行测试时实际检出的分支名或工作树路径；同时使用工作树时可写为 `<分支名>（<工作树路径>）`。
- `归属基线`必须填写可追溯的远程基线分支，优先使用 `origin/<branch>`，不能只写模糊的“主干”或“最新代码”。
- 灰度与非灰度使用不同分支、工作树或基线时分别如实填写，不得复制同一归属信息。
- 无法核实时填写“待确认”，不得猜测分支、工作树或基线。

每条用例的三级章节标题必须以测试结果状态开头，格式为 `### <状态 Emoji> <用例编号>：<用例名称>`，使目录直接显示执行状态：

- `### ✅ TC-...`：已测试且通过。
- `### ❌ TC-...`：已测试但失败。
- `### ⛔ TC-...`：执行受阻。
- `### ⏳ TC-...`：尚未测试。

标题状态必须与用例内的 `📊 测试结果`完全一致；执行或结果变化时同时更新两处。

用例编号必须全文档统一：灰度章节使用 `TC-GRAY-<三位序号>`，非灰度章节使用 `TC-FULL-<三位序号>`，各自从 `001` 起连续递增。编号一经写入不得复用、重排或修改；插入新用例时使用该章节下一个可用序号。矩阵引用必须使用完整编号。

同一环境章节内的相邻测试用例之间必须使用独立的 Markdown 分隔线 `---`。分隔线前后各保留一个空行；分隔线不能替代用例标题、字段或环境章节。

## 测试场景类型

每条用例必须归属一个场景类型，并在 `🎯 测试场景` 开头以 `[<场景类型>]` 标注。全部类型、典型场景与适用范围如下：

| 分类 | 场景类型 | 典型场景 | 适用范围 |
| --- | --- | --- | --- |
| 输入取值 | `正常` | 合法输入走通主路径 | 所有业务元素的基础类型；每个入口至少一条主路径用例 |
| 输入取值 | `异常` | 非法输入、无权限、资源不存在、下游显式失败 | 所有入口；带鉴权的入口必须覆盖无权限分支 |
| 输入取值 | `边界` | 空值/缺省、长度与数量极值、刚好越界值 | 有入参的接口、有上限的列表与分页、字段或枚举取值变更的数据结构 |
| 状态与交互 | `状态与顺序` | 非法状态迁移、重复迁移、未初始化调用、事件乱序到达 | 有状态机的业务（订单、工单）、按序消费的消息、依赖初始化的组件 |
| 状态与交互 | `并发与幂等` | 重复提交、消息重复投递、并发修改同一资源、乐观锁冲突 | 写接口、消息消费者、可重复触发的定时任务、并发修改的数据记录 |
| 状态与交互 | `超时与依赖故障` | 下游超时、部分失败、重试上限后的保留或降级路径 | 调用外部依赖（支付渠道、三方接口、跨服务）的链路 |
| 数据与配置 | `事务与一致性` | 回滚无残留、跨表/跨服务写的补偿、唯一约束冲突 | 跨集合/跨服务写入、带唯一约束的数据、可中断的迁移脚本 |
| 数据与配置 | `兼容性` | 存量旧数据、新旧接口或状态共存、枚举新增后的老消费方 | 数据结构变更、灰度期新旧版本共存、对外枚举或协议变更 |
| 数据与配置 | `配置与开关` | 开关两态、多开关叠加、配置缺省与非法值 | 功能开关、灰度标签、外部化配置项 |
| 时序与资源 | `时间与时钟` | 时区/夏令时、跨天/月末/闰年、定时任务漏触发或重复触发 | 定时任务、含时间计算的业务（账单、有效期、报表） |
| 时序与资源 | `资源与生命周期` | 连接/句柄/线程泄漏、连接池耗尽、执行中被停机 | 持有长连接或句柄的组件、受限资源池、可中断任务 |
| 质量属性 | `安全与越权` | 水平/垂直越权、注入、报文或日志泄露敏感信息 | 涉及资源归属或角色权限的接口必选；注入与泄露类选配 |
| 质量属性 | `性能与容量` | 大数据量、深分页、循环查库 | 功能侧量级验证选配；梯度并发与容量结论归 `$api-load-testing` |
| 质量属性 | `可观测性` | 关键分支日志/埋点存在且可判定，支撑失败定位 | 选配；关键链路变更建议纳入，预期以变更代码实际 logger 为准 |

## 结合业务选择场景类型

先识别本次变更涉及的业务元素，证据来源依次为：本次需求/PRD、分支 diff、已有的 `$code-link-tree-analysis` 链路树产出（仅引用已有结果，不自动触发该技能）。再按下表映射必选场景类型：

| 业务元素 | 必选场景类型 |
| --- | --- |
| HTTP/RPC 接口 | 正常、异常、边界；写接口加并发与幂等；涉及资源归属或角色时加安全与越权 |
| 消息消费者 | 正常、异常、并发与幂等（重复投递）、状态与顺序（乱序）、超时与依赖故障（消费失败、重试、死信） |
| 定时任务 | 正常、时间与时钟、并发与幂等（重复或并发触发互斥）、资源与生命周期（中断恢复） |
| 状态流转（订单、工单等状态机） | 正常、状态与顺序（非法迁移、重复迁移）、并发与幂等（并发迁移）；灰度期新旧状态共存时加兼容性 |
| 数据结构/集合变更 | 正常、兼容性（存量旧数据）、事务与一致性（唯一约束、写入中断）、边界（字段与枚举取值） |
| 外部依赖调用（支付渠道、三方接口） | 正常、异常（对端失败）、超时与依赖故障（超时、重试上限、降级）、并发与幂等（对端幂等性） |
| 配置/灰度开关 | 配置与开关（两态、组合、缺省、非法值）；每种关键组合补一条正常主路径用例 |

性能与容量、可观测性、注入类安全用例为选配项，默认不强制；纳入前结合业务风险与用户确认。

## 用例必填字段

每条用例必须按固定顺序写全以下字段，Emoji 与文字名称同时保留：

1. `🎯 测试场景`：以 `[<场景类型>]` 开头标注类型（如 `[并发与幂等] 验证…`），再说明验证什么行为及必要条件；类型必须能在场景覆盖矩阵中对应。
2. `🧰 前置条件`：写明登录授权、用户角色、服务状态、灰度/全量开关和依赖数据；不写真实密码或令牌。超时与依赖故障、并发与幂等、时间与时钟、状态与顺序（乱序）类用例必须写明触发手段（mock/故障注入、MQ 重发、并发脚本、可控时钟等）；无可用手段时写“触发手段：待确认”，不得虚构可执行的步骤。
3. `🗃️ 测试数据`：使用带语言标识的代码块展示实际使用的请求参数、账号属性、业务记录及灰度标签；补充必要的准备与清理说明，敏感值使用脱敏占位符。
4. `🧭 测试步骤`：使用有序步骤写出输入、操作和观察点，确保他人可复现；必须包含验证是否命中所属环境版本或开关的观察步骤。
5. `💡 测试预期`：使用带语言标识的代码块展示预期返回码、响应体、页面值或数据状态，并说明所属环境的版本命中情况；不得只写概括性结论。
6. `📥 返回结果`：使用带语言标识的代码块填写执行时得到的真实响应、页面值、状态、实际命中环境或数据变化；必须直接写在本测试计划文档中，不能只放外部链接。
7. `📊 测试结果`：填写 `✅ 通过`、`❌ 失败`、`⛔ 阻塞` 或 `⏳ 未执行`。

## 编写与回填规则

- 一个用例只验证一个独立行为；正常、异常、边界、状态与顺序、并发与幂等、超时与依赖故障等不同场景类型分别成例，不得把异常、并发或降级分支混进正常用例。
- 场景类型按业务元素映射选取，不追求每类都写；业务上不存在的类型在矩阵注明原因后不写用例，不得以排期或工作量为由留空。
- 覆盖矩阵与用例双向一致：矩阵引用的用例编号必须存在，每条用例的类型必须能在矩阵中找到；新增或删除用例时同步更新矩阵。
- 性能与容量用例只做功能侧量级验证（大数据量、深分页、循环查库）；梯度并发和容量结论由 `$api-load-testing` 产出，本计划不复制压测场景。
- 可观测性用例的预期写可直接 grep 的日志模板或埋点字段（含业务主键、traceId），内容以变更代码中的实际 logger 语句为准，不得虚构埋点。
- 灰度与非灰度必须分章节设计；不能把两类用例混排或只写“验证发布”。
- 环境归属信息是章节级必填内容，只写一次，并按三项列表展示；不要在每条用例中重复分支、工作树和基线。
- 步骤和预期是计划内容；返回结果和测试结果是执行事实，不能混写。
- 未执行时，返回结果和测试结果均写 `⏳ 未执行`，不得用预期内容代替实际结果。
- 新建用例的标题默认使用 `⏳`；执行后按结果改为 `✅`、`❌` 或 `⛔`，并同步更新 `📊 测试结果`。
- 失败或阻塞时保留实际返回结果，并用一句话说明差异或阻塞原因。
- 返回结果至少记录关键返回码、消息、页面提示、响应字段、状态变化或数据变化；不得只写“符合预期”。
- 测试数据、测试预期和已执行的返回结果必须使用 `json`、`sql`、`http`、`text` 等合适语言标识的代码块展示具体内容；简短说明只用于解释代码块。
- 数据量较大时允许展示部分数据，但必须在代码块前注明总记录数、展示范围和截取规则，并在代码块中使用明确的省略标记；不得因截取隐藏影响判定的字段或异常记录。
- 测试预期是执行前定义的精确预期，不得冒充真实结果；真实数据返回只填写在执行后的返回结果中。
- 不编造实际返回值或执行状态；未知信息写“待确认”。
- Emoji 只作视觉标识，不能单独替代字段名或文字状态。

## 复审检查

复审时只检查以下问题（编号集合、状态两处一致这类机械核对优先用脚本完成，如 grep 编号差集；人工聚焦覆盖与可复现性）：

- 是否存在「场景覆盖矩阵」「灰度环境」「非灰度环境」三个章节，且用例没有跨环境章节混排。
- 编写前是否已分别确认灰度环境和非灰度环境的测试分支/工作树；未确认时不得直接生成正式章节。
- 每个环境章节是否紧跟实际测试分支/工作树和远程归属基线，且两类环境信息没有误复用。
- 环境信息是否按“环境归属、测试分支/工作树、归属基线”三项分点展示，避免长句拼接。
- 每条用例标题是否以状态 Emoji 开头，且与 `📊 测试结果`一致。
- 同一环境章节内相邻用例之间是否使用独立的 `---` 分隔线，并保持空行。
- 是否每条用例都有七个必填字段，包括前置条件和测试数据。
- 灰度章节是否验证目标人群/流量命中，非灰度章节是否验证全量范围。
- 场景覆盖矩阵是否按业务元素映射选齐必选场景类型，未覆盖项是否写明业务上不存在的原因。
- 每条用例的 `🎯 测试场景` 是否标注场景类型；编号是否符合 `TC-GRAY-<三位序号>`/`TC-FULL-<三位序号>` 规则，矩阵引用与实际用例是否一一对应。
- 故障注入、并发、时钟、乱序类用例是否写明触发手段；无手段的是否标“待确认”而非硬编步骤。
- 状态与顺序、并发与幂等、超时与依赖故障类用例是否独立成例，未混入正常用例。
- 是否误把压测场景复制进计划；性能容量结论是否留给 `$api-load-testing`。
- 步骤是否可复现，预期是否可判定。
- 返回结果是否已直接记录在文档内，并与步骤对应。
- 测试数据、测试预期和已执行返回结果是否使用代码块展示具体数据；大数据截取是否标明总量与范围。
- 测试结果是否与预期和实际返回结果一致。
- 是否存在背景、流程、指标或链接等无助于执行/判定用例的噪音；有则删除。

需要复制用例骨架或查看完整示例时，读取 [references/test-plan-template.md](references/test-plan-template.md)。
