# 测试计划文档编写

## 核心目标

测试计划只保留两类信息：

1. 可执行的测试用例。
2. 用例执行后的实际返回结果与测试结果。

删除项目背景、排期、环境说明、角色职责、缺陷流程、发布门禁、泛化测试策略等与单条用例执行和判定无直接关系的内容。最多保留一行标题或版本范围用于定位。

## 文档分组

测试用例不得平铺，必须按以下顺序分为两个二级章节：

1. `## 灰度环境`：只放验证灰度目标用户、流量、标签、版本或开关的用例。
2. `## 非灰度环境`：只放验证非灰度用户、全量版本或默认开关的用例。

开始编写文档前，必须先向用户确认两个环境各自的测试分支（或工作树）：灰度环境测试分支、非灰度环境测试分支。两者均确认后再生成对应章节；任一分支未提供或无法核实时，先暂停生成并提出确认，不得猜测或用同一个分支代替两个环境。

同一业务场景需要同时验证灰度和非灰度时，在两个章节各写一条独立用例。章节已经表达环境类型，不再在每条用例中重复“验证模式”字段。

每个环境章节标题后必须紧跟环境归属信息，并按三项列表展示，避免把多项信息拼成一行：

```markdown
- 环境归属：<灰度/非灰度>
- 测试分支/工作树：<实际分支名或工作树路径>
- 归属基线：<远程基线分支，例如 origin/main>
```

- `测试分支/工作树`必须填写执行测试时实际检出的分支名或工作树路径；同时使用工作树时可写为 `<分支名>（<工作树路径>）`。
- `归属基线`必须填写可追溯的远程基线分支，优先使用 `origin/<branch>`，不能只写模糊的“主干”或“最新代码”。
- 灰度与非灰度使用不同分支、工作树或基线时分别如实填写，不得复制同一归属信息。
- 无法核实时填写“待确认”，不得猜测分支、工作树或基线。

每条用例的三级章节标题必须以测试结果状态开头，格式为 `### <状态 Emoji> <用例编号>：<用例名称>`，使目录直接显示执行状态：

- `### ✅ TC-...`：已测试且通过。
- `### ❌ TC-...`：已测试但失败。
- `### ⛔ TC-...`：执行受阻。
- `### ⏳ TC-...`：尚未测试。

标题状态必须与用例内的 `📊 测试结果`完全一致；执行或结果变化时同时更新两处。

同一环境章节内的相邻测试用例之间必须使用独立的 Markdown 分隔线 `---`。分隔线前后各保留一个空行；分隔线不能替代用例标题、字段或环境章节。

## 用例必填字段

每条用例必须按固定顺序写全以下字段，Emoji 与文字名称同时保留：

1. `🎯 测试场景`：说明验证什么行为及必要条件。
2. `🧰 前置条件`：写明登录授权、用户角色、服务状态、灰度/全量开关和依赖数据；不写真实密码或令牌。
3. `🗃️ 测试数据`：使用带语言标识的代码块展示实际使用的请求参数、账号属性、业务记录及灰度标签；补充必要的准备与清理说明，敏感值使用脱敏占位符。
4. `🧭 测试步骤`：使用有序步骤写出输入、操作和观察点，确保他人可复现；必须包含验证是否命中所属环境版本或开关的观察步骤。
5. `💡 测试预期`：使用带语言标识的代码块展示预期返回码、响应体、页面值或数据状态，并说明所属环境的版本命中情况；不得只写概括性结论。
6. `📥 返回结果`：使用带语言标识的代码块填写执行时得到的真实响应、页面值、状态、实际命中环境或数据变化；必须直接写在本测试计划文档中，不能只放外部链接。
7. `📊 测试结果`：填写 `✅ 通过`、`❌ 失败`、`⛔ 阻塞` 或 `⏳ 未执行`。

## 编写与回填规则

- 一个用例只验证一个独立行为；正常、异常、边界行为分别成例。
- 灰度与非灰度必须分章节设计；不能把两类用例混排或只写“验证发布”。
- 环境归属信息是章节级必填内容，只写一次，并按三项列表展示；不要在每条用例中重复分支、工作树和基线。
- 步骤和预期是计划内容；返回结果和测试结果是执行事实，不能混写。
- 未执行时，返回结果和测试结果均写 `⏳ 未执行`，不得用预期内容代替实际结果。
- 新建用例的标题默认使用 `⏳`；执行后按结果改为 `✅`、`❌` 或 `⛔`，并同步更新 `📊 测试结果`。
- 失败或阻塞时保留实际返回结果，并用一句话说明差异或阻塞原因。
- 返回结果至少记录关键返回码、消息、页面提示、响应字段、状态变化或数据变化；不得只写“符合预期”。
- 测试数据、测试预期和已执行的返回结果必须使用 `json`、`sql`、`http`、`text` 等合适语言标识的代码块展示具体内容；简短说明只用于解释代码块。
- 数据量较大时允许展示部分数据，但必须在代码块前注明总记录数、展示范围和截取规则，并在代码块中使用明确的省略标记；不得因截取隐藏影响判定的字段或异常记录。
- 测试预期是执行前定义的精确预期，不得冒充真实结果；真实数据返回只填写在执行后的返回结果中。
- 不编造实际返回值或执行状态；未知信息写“待确认”。
- Emoji 只作视觉标识，不能单独替代字段名或文字状态。

## 复审检查

复审时只检查以下问题：

- 是否存在独立的“灰度环境”和“非灰度环境”章节，且用例没有跨章节混排。
- 编写前是否已分别确认灰度环境和非灰度环境的测试分支/工作树；未确认时不得直接生成正式章节。
- 每个环境章节是否紧跟实际测试分支/工作树和远程归属基线，且两类环境信息没有误复用。
- 环境信息是否按“环境归属、测试分支/工作树、归属基线”三项分点展示，避免长句拼接。
- 每条用例标题是否以状态 Emoji 开头，且与 `📊 测试结果`一致。
- 同一环境章节内相邻用例之间是否使用独立的 `---` 分隔线，并保持空行。
- 是否每条用例都有七个必填字段，包括前置条件和测试数据。
- 灰度章节是否验证目标人群/流量命中，非灰度章节是否验证全量范围。
- 步骤是否可复现，预期是否可判定。
- 返回结果是否已直接记录在文档内，并与步骤对应。
- 测试数据、测试预期和已执行返回结果是否使用代码块展示具体数据；大数据截取是否标明总量与范围。
- 测试结果是否与预期和实际返回结果一致。
- 是否存在背景、流程、指标或链接等无助于执行/判定用例的噪音；有则删除。
