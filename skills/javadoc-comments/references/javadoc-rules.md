## 基本原则

### 对齐 JDK 与 Javadoc 惯例

- 使用 `/** ... */` 编写可生成 API 文档的文档注释，使用 `//` 或 `/* ... */` 解释实现细节。
- 把文档注释放在注解之前、声明紧邻位置；不要放在声明之后。
- 摘要写成完整、简洁的中文句子且不依赖后文。JDK 10 及以上优先在主描述开头使用 `{@summary ...}` 明确摘要；旧版本把摘要放在独立首段，详细说明从新的 `<p>` 开始，并通过项目 Javadoc 任务确认摘要截取正确。
- 使用 `{@code ...}` 表示关键字、字面量和短代码，使用 `{@link ...}` 引用可解析的 Java 元素。
- 在传统 `/** ... */` 文档中使用合法 HTML；用 `{@literal ...}` 或 `{@code ...}` 处理可能被解析为标记的 `<`、`>` 和 `&`。
- 描述公开契约，不暴露无关实现细节。项目已注册扩展标签时，可使用 `@implSpec`、`@implNote`；否则使用普通正文或实现注释。
- 遵循项目配置的 `doclint`（文档检查器）、`Checkstyle`（代码风格检查工具）或格式化规则；本规范不覆盖更严格的仓库规则。

### 信息密度

优先记录以下内容：

- 元素承担的职责以及与相邻组件的边界。
- 参数允许的范围、格式、单位、时区、编码、是否可为 `null`。
- 返回值语义、空集合与 `null` 的区别、是否返回快照或可变视图。
- 可观察副作用、状态变化、资源所有权和调用顺序。
- 抛出异常的可验证条件，而不是简单重复异常类名。
- 并发、幂等、缓存、重试和性能约束，但仅限代码、测试或既有文档能够证明的内容。
- 反直觉实现背后的原因、兼容性要求或权衡。

避免以下内容：

- “获取名称”“设置值”“循环列表”等代码复述。
- 作者、日期、工单号等版本控制系统已经能可靠记录的信息，除非项目明确要求。
- 无法验证的保证，如“线程安全”“永不为空”“高性能”。
- 仅凭类型名或单个签名推断“扩展点”“适配器”“缓存策略”等架构角色；证据不足时使用中性描述。
- `TODO`（待办事项）、`FIXME`（待修复事项）中只有英文而没有中文解释。
- 复制方法名或参数名后换一种中文重复。

## 文档覆盖范围

至少为以下元素提供 Javadoc：

- 对外公开或受保护的类型、构造器、方法和字段。
- 作为扩展点、服务提供者接口或跨模块契约的包级可见元素。
- `package-info.java` 中的包职责、边界和关键使用约束。
- `module-info.java` 中模块用途及导出、使用或提供服务的必要说明。
- 即使不是公开 API，但行为复杂、容易误用或承担关键业务规则的元素。

可省略或使用 `{@inheritDoc}`：

- 完全继承父类型契约且没有附加行为的重写方法。
- 语义显而易见、无额外约束的私有辅助方法。
- 编译器生成或工具生成且应从生成源维护的代码。

## Javadoc 结构

建议按以下结构组织：

1. 摘要。JDK 10 及以上优先使用位于主描述开头的 `{@summary ...}`；旧版本使用独立的中文摘要首段。
2. 必要的详细说明，可分段使用 `<p>`；不要用单独的 `</p>` 结束标签，除非项目规则要求。
3. 项目构建明确支持时，使用 API 说明扩展标签 `@apiNote`。
4. 项目构建明确支持时，使用实现契约扩展标签 `@implSpec`。
5. 项目构建明确支持时，使用实现说明扩展标签 `@implNote`。
6. 标准块标签，按统一顺序排列。

不要为了凑结构添加空段落或空标签。使用 `{@summary ...}`、`{@snippet ...}` 或 Markdown 文档注释前，先按 [version-and-validation.md](version-and-validation.md) 确认项目支持的 JDK 版本和现有风格。

示例：

```java
/**
 * 根据用户标识查询当前有效的账户快照。
 *
 * <p>返回值是查询时刻的只读快照，后续账户变更不会反映到该对象中。
 *
 * @param userId 用户唯一标识，不能为 {@code null}
 * @return 当前有效的账户快照
 * @throws IllegalArgumentException 当 {@code userId} 为空字符串时抛出
 * @throws AccountNotFoundException 当用户不存在有效账户时抛出
 */
AccountSnapshot findAccount(String userId);
```

## 标签规则与顺序

同一代码库保持以下顺序：

1. `@apiNote`：仅在项目注册该扩展标签时
2. `@implSpec`：仅在项目注册该扩展标签时
3. `@implNote`：仅在项目注册该扩展标签时
4. `@author`、`@version`：仅用于类型，且仅在项目明确要求时添加
5. `@param`：先类型参数，再普通参数；顺序与声明一致
6. `@return`
7. `@throws`：按签名或业务流程的稳定顺序
8. `@see`
9. `@since`
10. `@serial`、`@serialField`、`@serialData`
11. `@deprecated`

项目已有顺序与此不同但内部一致时，遵循项目顺序。

### `@param`

- 每个类型参数和形式参数各写一个标签，名称必须与签名完全一致。
- 类型参数写为 `@param <T>`，说明其角色和约束。
- 说明语义、范围、格式、单位和空值约定，不写“参数 xxx”。

### `@return`

- 非 `void` 方法必须说明返回值语义。默认使用块标签 `@return`；JDK 16 及以上可在方法主描述开头使用内联 `{@return ...}` 同时生成摘要和返回值说明，但不得与块标签重复。
- 构造器和 `void` 方法不得使用块级或内联返回值标签。
- 明确 `null`、空集合、特殊值、可变性或所有权约定。
- 不写“返回结果”“返回对象”等无信息内容。

### `@throws`

- 使用 `@throws`，除非项目统一使用同义的 `@exception`。
- 说明调用者可理解和处理的触发条件。
- 文档化签名声明的受检异常，以及调用者需要知道的重要运行时异常。
- 不声明实现不可能抛出的异常，也不把底层异常机械复制到公共契约。

### `@since` 与 `@deprecated`

- 仅在能够确认版本号时写 `@since`，不要猜测版本。
- 废弃元素同时使用 `@Deprecated` 和 `@deprecated`。在版本可确认时说明从哪个版本起废弃，并说明原因、替代方案和迁移方式；用 `{@link ...}` 指向替代 API。使用 `since` 或 `forRemoval` 注解元素前先确认源码级别至少为 Java 9。

### 内联标签

- `{@code value}`：关键字、常量、短表达式和无法解析为链接的标识符。
- `{@link Type#method(...)}`：相关类型或成员，链接文本无需重复写英文说明。
- `{@linkplain ...}`：需要普通字体的链接文本。
- `{@literal ...}`：需要按字面显示的 `<`、`>`、`&` 等字符。
- `{@value ...}`：引用静态常量的值，避免在注释中复制可能变化的字面量。
- `{@inheritDoc}`：继承父类型文档；存在新增前置条件、副作用或异常时必须补充差异。

## 各类元素规则

### 类与接口

说明职责、生命周期、协作边界、线程安全和典型用法。只有能从实现或既有契约确认时才写线程安全结论。

```java
/**
 * 管理订单状态转换，并保证每次转换符合订单状态机约束。
 *
 * <p>该类型不是线程安全的；调用方必须为同一实例提供外部同步。
 */
public final class OrderStateMachine {
}
```

### 枚举

说明枚举整体表达的概念，并为含义不直观的枚举常量补充说明。不要只把英文常量名直译一遍。

### 记录

说明记录表达的不变量，并使用 `@param` 记录每个组件的契约。若显式声明访问器或紧凑构造器存在额外行为，再单独记录差异。

### 注解类型

说明适用目标、处理时机、继承或重复规则和默认值语义。注解元素的 Javadoc 说明其值如何影响行为。

### 构造器

说明创建后的对象状态、依赖所有权、参数约束和失败条件。不要写“创建一个实例”后便结束。

### 方法

以调用者视角说明行为和契约。对异步方法说明完成时机、失败承载方式和取消语义；首次出现时写“异步（asynchronous）”等中文翻译。

### 字段与常量

说明单位、取值范围、特殊值、可见性含义和是否可变。常量名已完整表达语义且无额外契约时，不必重复注释。

### 包与模块

- `package-info.java`：说明包的职责、入口类型、依赖方向和关键约束。
- `module-info.java`：说明模块提供的能力；只对需要解释的 `exports`、`uses`、`provides` 等指令补充注释。

## 普通注释规则

- 优先使用短小的 `//` 解释局部决策和非显然分支。
- 多段实现说明可使用 `/* ... */`，但不要伪装成 Javadoc。
- 注释放在所解释代码之前，并与代码保持相同缩进。
- 解释原因和不变量，例如兼容旧协议、规避竞态条件、保持排序稳定；不要叙述下一行代码。
- 修改实现时同步验证相邻注释。注释过时等同于缺陷。

不推荐：

```java
// 用户数量加一
userCount++;
```

推荐：

```java
// 预留索引 0 表示“未分配”，因此实际用户索引从 1 开始。
int nextUserIndex = userCount + 1;
```

## 英文翻译规则

### 必须翻译

- 普通英文句子、标题、警告和待办事项。
- 有语义的技术术语和缩写，例如“垃圾回收（Garbage Collection，GC）”。
- 外部协议或算法概念，例如“指数退避（exponential backoff）”。
- 错误消息含义的引用说明；错误消息字面量本身保持不变。

### 保持原样

- Java 标识符、包名、类名、方法名、字段名和枚举常量。
- Javadoc 标签、注解、命令、文件路径、URL、配置键和协议字段。
- 代码片段、字符串字面量和必须精确匹配的外部值。
- 许可证文本、版权声明和明确标注的自动生成内容；不要擅自翻译或改写。

### 推荐写法

```java
/**
 * 使用最近最少使用（Least Recently Used，LRU）策略淘汰缓存项。
 *
 * @implNote 淘汰操作采用“写时复制”（copy-on-write）机制，避免读取路径持有写锁。
 */
```

```java
// 服务端要求使用 X-Request-Id（请求标识）头进行链路关联。
```

不要写：

```java
// Use fallback when cache miss.
```

应写：

```java
// 缓存未命中（cache miss）时回退到持久化存储。
```

## 示例

### 泛型方法

```java
/**
 * 将输入元素转换为不可变列表，并保持原有迭代顺序。
 *
 * @param <T> 输入元素类型
 * @param source 输入元素，不得为 {@code null}，且不能包含 {@code null} 元素
 * @return 保持输入顺序的不可变列表
 * @throws NullPointerException 当 {@code source} 或其中任一元素为 {@code null} 时抛出
 */
<T> List<T> immutableCopy(Iterable<? extends T> source);
```

### 废弃方法

```java
/**
 * 使用旧格式解析时间戳。
 *
 * @param value 待解析的旧格式时间戳文本
 * @return 解析后的时间点
 * @deprecated 自 2.1 起废弃。旧格式不包含时区信息，请改用
 *             {@link #parseTimestamp(String, ZoneId)}。
 */
@Deprecated(since = "2.1", forRemoval = true)
Instant parseLegacyTimestamp(String value);
```

### 继承文档并补充差异

```java
/**
 * {@inheritDoc}
 *
 * @implNote 本实现使用无锁（lock-free）队列减少竞争，但不保证严格公平。
 */
@Override
public void submit(Task task) {
    // 实现省略。
}
```

## 审查清单

- 文档注释位置和 `/** ... */` 形式正确。
- 首句是完整中文摘要，并能在摘要表中独立成立。
- 类型参数、参数、返回值和异常标签与签名一一对应。
- 标签顺序与项目保持一致，没有无效链接和错误引用。
- 英文术语首次出现时提供中文翻译，固定代码元素保持原样。
- 注释描述真实行为，没有猜测或过度承诺。
- 没有逐行复述代码、无意义占位注释或过期说明。
- 重写方法正确选择 `{@inheritDoc}` 或补充差异。
- 废弃文档包含原因、替代 API 和迁移方向。
- 纯注释任务的 diff 不包含业务逻辑、签名或格式化噪声。
