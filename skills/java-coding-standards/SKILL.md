# 编码规范

## 目标与设计思路

把“风格偏好”转化为编码前可执行的设计和实现约束。规范必须在写代码前帮助确定职责、命名、流程、边界和性能策略，而不是等代码完成后再被动整改。

采用三层设计：

1. **项目层**：优先遵守 `AGENTS.md`、贡献指南、构建配置、已有 lint/formatter 和相邻代码的稳定惯例。
2. **语言层**：只补充当前语言和框架的通用最佳实践，避免与项目事实冲突。
3. **执行层**：每条规则都绑定检查方式、例外条件和修复建议；能自动化的交给工具，不能自动化的进入评审清单。

## 编码前置工作流

1. **确定实现范围**：明确业务目标、输入输出、边界条件、涉及模块和允许修改的文件。
2. **收集项目事实**：读取仓库级指令、构建/依赖配置、Formatter/Lint、测试约定、目标文件和相邻实现；不得把猜测写成规则。
3. **识别技术模型**：确定语言、版本、框架、运行模型和编程范式，并选择 `references/adapters/` 中的适配规则；不确定时标注假设并回退到通用规则，禁止一刀切。
4. **先做设计再编码**：先写出业务术语、职责边界、主流程、错误边界、数据访问和性能策略；确认方法、类、组件不会无故超限。
5. **按设计直接实现**：使用具名业务方法、线性流程和最小必要抽象；将纯逻辑、校验、查询、规则和副作用放在合适边界。
6. **边写边验证**：同步检查命名、复杂度、资源释放、并发/异步模型和性能敏感路径，发现偏离设计立即调整，不把问题留到事后。
7. **交付前验证**：运行与改动匹配的格式检查、静态检查、单元测试和构建，记录实际命令及结果；无法运行时说明原因和剩余风险。

## 编码输出要求

- 编码前先输出简短的“适用规范与设计约束”，再开始实现；避免只给事后问题列表。
- 实现说明应包含业务流程、职责拆分、关键命名和性能策略；必要时说明为何不采用更复杂的抽象。
- 若用户要求审查，再引用文件和行号，按严重级别说明现象、风险、修复和验证方式。
- 规范文档使用“必须/禁止/应该/可以”等明确措辞，并给出最小正例和反例。
- 日志埋点坚持核心必要原则：只记录故障定位、关键业务结果、审计或明确运营用途；禁止用大量无效日志替代指标、追踪和代码阅读。
- 项目现有规则与通用建议冲突时，以项目规则为准，并指出冲突来源。
- 例外必须有边界和理由，例如性能热点、生成代码、第三方协议字段或兼容性要求。
- 命名必须优先采用业务术语；避免 `data`、`info`、`result`、`process` 等无法表达领域含义的名称。
- 注释必须服务于业务理解和维护决策：解释为什么、业务约束、算法复杂度、并发/异步边界和非显然副作用；禁止逐行翻译代码或用注释掩盖复杂实现。
- Javadoc 禁止使用单行 `/** ... */`；任何 Javadoc 都必须统一展开为多行格式。
- 对公共 API、领域规则、状态转换、异常补偿、性能敏感路径和临时兼容逻辑必须补充注释；简单的自解释代码不强制添加注释。
- 不为一次性问题创建抽象；不在无关文件中顺手格式化或重命名。

## 规则分类

至少覆盖以下类别，并按任务需要裁剪：命名与目录、格式与注释、类型与 API、错误处理、日志与敏感信息、并发与资源生命周期、分层与依赖、测试、性能、可观测性和工具门禁。日志级别、统一前缀和请求链路 MDC 规则见 [references/logging.md](references/logging.md)。通用注释细则见 [references/commenting.md](references/commenting.md)；Java 注释必须同时遵循 [references/java-javadoc.md](references/java-javadoc.md) 和 [references/java-javadoc-validation.md](references/java-javadoc-validation.md)。跨语言差异和示例按需读取 [references/language-adaptation.md](references/language-adaptation.md) 与 `references/adapters/`。

编码示例按需读取 `references/examples/`，当前以 Java 为统一示例语言，按业务场景选择命令式、响应式、函数式、异步或并发实现。每个示例文件都包含一个完整代码示例；不得机械复制，必须结合项目约束、数据规模和运行模型调整。

## 编码完成检查

- [ ] 已读取并遵守仓库级指令与现有工具配置。
- [ ] 规则有明确范围、优先级、例外和验证方式。
- [ ] 审查结论区分事实、推断和待确认项。
- [ ] 关键风险（安全、正确性、并发、资源、错误处理）已优先检查。
- [ ] 日志级别、统一前缀、敏感字段和完整请求链路 MDC 已按项目约定设计并验证。
- [ ] 注释已覆盖公共 API、业务规则、状态转换和非显然性能/并发约束，且没有无效或过期注释。
- [ ] 已运行可用的格式、静态检查、测试或构建，并如实报告结果。
- [ ] 规范变更有迁移顺序，避免一次性制造不可审查的大 diff。
