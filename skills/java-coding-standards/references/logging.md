# Java 日志埋点与请求链路规范

## 适用范围

本规范用于 Java 服务、定时任务、消息消费者、异步任务和下游客户端的编码前设计。先检查项目已有日志门面、结构化日志格式、采集字段和追踪系统；若项目已有约定更严格，沿用项目约定，并只补充缺失字段。

## 设计原则

- **核心必要原则**：只有当日志能帮助定位故障、解释关键业务结果、满足审计要求或驱动明确的运营动作时才输出；无法回答“谁需要看、看后做什么”的日志禁止添加。
- 一次事件优先保留一条有上下文的日志，不在 Controller、Service、Repository 和客户端层层重复打印同一事件。
- 日志用于回答“发生了什么、影响哪个业务对象、是否需要处理”，不是复制代码执行过程。
- 统一使用项目日志门面（通常为 SLF4J），禁止在业务代码中直接依赖具体日志实现或使用 `System.out`、`System.err`。
- 优先结构化参数和固定字段，禁止字符串拼接；避免在低级别日志中提前构造昂贵对象。
- 日志字段使用稳定的英文 `snake_case` 名称，字段值使用业务可理解的枚举或脱敏值。

### 输出前的必要性判断

新增一条日志前必须至少满足以下一项，并在设计中指出用途：

| 目的 | 应记录的内容 | 不应记录的内容 |
| --- | --- | --- |
| 故障定位 | 失败阶段、错误码、关键业务 ID、处理动作 | 每个方法进入/退出、完整堆栈重复打印 |
| 业务结果 | 状态变更、处理结果、拒绝原因、幂等命中 | 每个字段赋值、无业务意义的中间变量 |
| 审计追踪 | 操作主体、资源、结果、时间和链路标识 | 敏感原文、无责任人的调试信息 |
| 运营分析 | 低频关键事件或聚合摘要 | 用逐请求日志代替计数、耗时和分布指标 |

以下日志默认禁止：方法入口/出口日志、每次循环日志、完整请求与响应体、SQL 全文、对象 `toString()`、重复异常堆栈、纯“开始处理/处理完成”但没有业务结果的日志。

## 日志级别决策

### `INFO`

记录正常且对运营、审计或容量分析有价值的业务事件：请求完成、订单状态变更、消息成功消费、定时任务完成、关键配置加载结果。

必须包含事件名、结果、耗时（若有）、核心业务标识和链路标识。高频健康请求、每条循环记录和完整请求体不得默认使用 `INFO`，否则使用 `DEBUG` 或指标。

### `WARN`

记录当前请求仍可完成，但存在需要关注的异常情况：降级、重试、使用默认值、临时兼容分支、接近阈值的资源、下游慢但成功返回。

必须说明影响范围、采取的兜底动作和是否需要告警。可预期的用户输入错误、正常业务拒绝和客户端取消通常不应使用 `WARN`，除非项目明确要求统计。

### `ERROR`

记录请求或任务失败、数据一致性风险、不可恢复的基础设施异常、消息无法处理或需要人工介入的情况。

只在最终处理边界记录一次异常堆栈；必须带 `trace_id`、业务标识、失败阶段、错误码和可执行的处理上下文。不要在底层捕获后打印 `ERROR` 再向上抛出，避免重复告警。

### `DEBUG` / `TRACE`

用于开发排错和低频诊断，例如规则分支、下游请求摘要、状态机输入输出摘要。必须避免敏感信息和大对象；生产环境默认关闭或按请求/组件动态开启。不得依赖 `DEBUG` 日志作为业务审计记录。

### 日志量门槛

- 关键链路以“入口必要上下文 + 关键结果/失败”作为最小集合；正常成功路径不超过一条 `INFO`，失败路径不超过一条最终 `ERROR`。
- 可聚合的数据使用指标、分布统计或定期汇总日志，不用高频明细日志承载。
- 需要临时增加诊断日志时必须限定组件、级别、采样率和失效时间；问题解决后删除或恢复默认级别。
- 生产日志量、单条日志大小和字段基数必须纳入容量评估；禁止把高基数用户输入作为索引字段。

## 关键节点与全链路耗时

### 埋点范围

- **全链路耗时**：在 HTTP/RPC 请求、消息消费、定时任务或异步任务的最终边界记录一次，从入口接收时间开始，到响应发送、消息确认或任务结束为止。
- **关键节点耗时**：只为会影响用户体验、稳定性或容量的边界埋点，例如数据库查询、外部 RPC、缓存访问、消息发布、文件存储和核心规则计算。普通私有方法不得单独埋点。
- 关键节点必须先登记稳定的 `stage` 名称，例如 `db_load_order`、`payment_rpc`、`publish_event`；禁止使用方法名、动态 URL 或用户输入作为节点名。
- 高频节点的详细耗时优先进入直方图/分布指标；确需日志时，使用采样或只记录超阈值事件，避免每个节点产生一条 `INFO`。

### 统一字段

耗时日志至少包含：

| 字段 | 含义 |
| --- | --- |
| `elapsed_ms` | 当前节点耗时，单位毫秒 |
| `total_elapsed_ms` | 从入口到当前完成边界的总耗时，仅在全链路日志使用 |
| `stage` | 稳定的关键节点名称 |
| `outcome` | `success`、`failed`、`timeout`、`cancelled` 等固定结果 |
| `timeout_ms` | 适用时记录配置的超时时间，便于判断是否逼近阈值 |

耗时使用单调时钟（Java 通常为 `System.nanoTime()`）计算，不能用墙上时钟计算耗时。日志字段统一使用毫秒；需要更高精度时写入指标，不在普通日志中输出纳秒。

### 级别与阈值

- 全链路成功日志可以携带 `total_elapsed_ms`；若请求本身不产生业务结果，则使用访问日志或指标，不额外新增 `INFO`。
- 关键节点成功耗时默认写入指标或 `DEBUG`；只有节点本身是关键业务结果、审计事件或项目明确要求时才使用 `INFO`。
- 节点或全链路超过项目定义的慢阈值使用 `WARN`，必须同时记录实际耗时、阈值、`stage` 和采取的动作。
- 因超时、失败或取消结束使用 `ERROR`（若需要人工介入）或项目约定的业务级别，并保留总耗时和失败阶段；同一异常仍只在最终边界记录一次。

示例（关键节点耗时并汇总到一次完成日志）：

```java
long requestStarted = System.nanoTime();
long nodeStarted = System.nanoTime();
PaymentResult payment = paymentClient.authorize(command);
long paymentElapsedMs = (System.nanoTime() - nodeStarted) / 1_000_000;

if (paymentElapsedMs > paymentSlowThresholdMs) {
    logger.warn("[order-service][payment][payment_rpc][slow] stage=payment_rpc elapsed_ms={} timeout_ms={} order_id={}",
        paymentElapsedMs, paymentTimeoutMs, orderId);
}

long totalElapsedMs = (System.nanoTime() - requestStarted) / 1_000_000;
logger.info("[order-service][order][order_created][success] order_id={} total_elapsed_ms={} payment_elapsed_ms={}",
    orderId, totalElapsedMs, paymentElapsedMs);
```

示例中的节点日志只在超过阈值时输出；正常节点耗时通过结构化字段或指标保留，避免关键链路出现大量无效日志。

## 统一日志前缀

每条业务日志必须带统一前缀，推荐格式：

```text
[应用名][模块名][事件名][结果]
```

例如：

```java
logger.info("[order-service][payment][payment_authorized][success] order_id={} amount={} elapsed_ms={}",
    orderId, amount, elapsedMs);
```

前缀字段必须来自稳定配置或常量，禁止在不同类中自行拼写变体。若日志平台已经提供独立的 `service`、`module`、`event`、`result` 字段，可保留可检索的短前缀，但不得同时产生两套含义冲突的字段。

## 完整请求链路与 MDC

### 必备字段

统一定义以下 MDC 字段；项目已采用 W3C Trace Context 或 OpenTelemetry 时，映射到现有字段，不重复创建平行标识：

| 字段 | 含义 | 生成与传递规则 |
| --- | --- | --- |
| `trace_id` | 一次完整请求/消息链路的全局标识 | 入口优先接收合法上游值，否则生成；跨线程、异步回调、消息和下游调用必须传递 |
| `span_id` | 当前服务内的操作节点标识 | 由追踪组件或边界拦截器生成，不在业务方法中手写 |
| `request_id` | 当前服务入口请求标识 | HTTP 请求、消息投递、任务执行各自生成；重试尝试不覆盖原始 `trace_id` |
| `parent_request_id` | 上游服务请求标识 | 有上游请求头时保留，缺失时不伪造 |
| `service_name` | 服务或应用名 | 从部署配置注入，禁止由业务代码临时设置 |
| `operation` | 当前入口操作名 | 使用稳定的路由、消息类型或任务名，不使用用户输入 |
| `tenant_id` | 租户标识（如适用） | 仅记录经过鉴权且允许出现在日志中的值 |
| `actor_id` | 操作主体标识（如适用） | 只记录脱敏或内部安全标识 |

### 生命周期要求

1. 在 HTTP、RPC、消息和定时任务入口创建或接收上下文，并在进入业务代码前写入 MDC。
2. 通过线程池、`CompletableFuture`、响应式链、协程适配器或消息重试传播上下文；不能假设 MDC 会自动跨线程继承。
3. 在 `finally`、请求过滤器结束回调或等价生命周期钩子中清理 MDC，避免线程复用导致串链。
4. 嵌套操作需要临时覆盖字段时使用可恢复的上下文（保存旧值并在 `finally` 恢复），禁止直接清空上游字段。
5. 日志模板不把 `trace_id` 等字段硬编码在每条消息中；优先由结构化日志布局统一输出，避免字段缺失或格式不一致。

示例（同步入口）：

```java
try (MdcScope ignored = MdcScope.open(Map.of(
    "trace_id", traceId,
    "request_id", requestId,
    "operation", "create_order"))) {
    logger.info("[order-service][order][order_created][success] order_id={}", orderId);
    return service.create(command);
}
```

`MdcScope` 仅表示项目已有的上下文封装；若项目使用 WebFilter、HandlerInterceptor、OpenTelemetry 或日志框架原生集成，应使用现有组件，不要重复实现一套上下文传播器。

## 脱敏与内容边界

- 禁止记录密码、令牌、Cookie、完整身份证件、银行卡号、支付凭证、私钥和完整请求体。
- 用户手机号、邮箱、地址、账户号等个人或财务信息只记录经过项目批准的掩码、哈希或内部 ID。
- 异常堆栈可以记录在受控日志系统，但消息文本不得包含敏感原文；返回给用户的错误信息与日志内部信息分离。
- 大列表、二进制、SQL 全文和响应正文使用摘要、数量、大小或哈希替代。

## 性能与验证

- 高频路径优先使用指标（计数、耗时、分布）而非逐请求 `INFO`；日志采样必须保留错误、慢请求和链路完整性。
- 使用参数化日志和级别判断保护昂贵计算；不要为了写日志重复序列化实体。
- 为入口、异常边界、异步传播和清理路径编写测试或集成验证，确认同一 `trace_id` 能贯穿完整链路且请求结束后 MDC 为空。
- 交付前检查：级别是否准确、前缀是否统一、关键节点和全链路耗时是否可观测、字段是否脱敏、异常是否只记录一次、MDC 是否跨线程传播并清理。
