# 注释规范

## 注释目标

注释用于补充代码无法直接表达的业务语义、设计原因和运行约束。优先通过清晰命名和合理拆解表达“做什么”，使用注释解释“为什么这样做、不能怎么做、变更会影响什么”。

## 必须注释的场景

- 公共类、公共方法、API、事件和配置项：说明用途、输入输出、失败语义和兼容约束。
- 业务规则和状态转换：说明规则来源、前置条件、状态含义和例外分支。
- 非显然算法、复杂度、缓存策略、批量/分页策略和性能热点。
- 并发、锁、线程池、事件循环、异步链、背压、取消和资源生命周期边界。
- 临时兼容逻辑、第三方协议限制、数据迁移和待移除代码：说明原因、影响和清理条件。
- 安全相关决策：权限边界、脱敏、幂等、重放防护和输入校验原因。

## 不应添加的注释

- 不要逐行翻译代码，例如 `// 将 count 加 1`。
- 不要用注释替代命名、拆解或错误处理。
- 不要保留与实现不一致的过期注释；修改代码时同步更新注释。
- 不要在注释中复制大段需求文档、日志或第三方源码。
- 不要写没有责任人的永久 `TODO`；临时事项必须说明原因、跟踪项和移除条件。

## Java 写法

- 公共 API 使用 Javadoc，说明参数、返回值、异常和线程/阻塞约束；完整 Java 规则见 [java-javadoc.md](java-javadoc.md)。
- 类内业务规则使用紧邻代码的块注释或短句注释，避免远离实际逻辑。
- 注释语言跟随项目约定；没有约定时，业务代码可使用团队主要语言，技术标识保留英文。
- 注释应短而具体，优先说明约束和原因，不写空泛评价。
- 禁止使用单行 `/** ... */` Javadoc；即使只有一句话，也必须展开为多行 `/**`、` * ...`、` */` 形式。

Java 注释任务还必须执行 [java-javadoc-validation.md](java-javadoc-validation.md) 中的版本识别、Javadoc、`doclint` 和 diff 校验流程。

## 编码前检查

在设计阶段先标记需要解释的业务决策和运行时边界；编码完成后检查注释是否覆盖这些决策，并确认代码变更不会使注释失效。
