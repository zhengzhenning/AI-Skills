# 编码详细设计规范

## 目标

产出能直接指导编码、测试和评审的轻量详细设计文档，使读者先快速判断：接口/任务怎么走、涉及哪些表及关系，再查看必要约束。

保持措辞简洁、逻辑清晰、内容干练、信息负载轻量化。优先使用清单、表格和短段落，删除不影响实现判断的背景和重复说明。

## 工作流程

1. 阅读仓库中的 `AGENTS.md`、贡献指南、现有接口、任务、表结构、测试和同类设计文档，项目规则优先。
2. 明确目标、范围、非目标、参与模块和外部依赖。无法验证的信息放入“待确认项”，不得猜测。
3. 先建立实现清单，再按接口或任务建立独立设计单元；为接口、任务、数据表/集合、业务事件和日志分配稳定编号。
4. 默认采用“实现清单 → 主逻辑 → 数据表关系 → 关键约束”的四段结构。每个接口/任务必须有流程图、时序图、3-7 步交互序列和成功/失败出口；安全、异常、一致性、日志、性能合并为关键约束，只写影响实现的内容。
5. 严格使用标识格式：单个表字段为 `表名.字段名`；同一表的多个字段合并为 `表名.字段1/字段2`；实体字段为 `实体名.字段名`；方法为 `类名.方法名`；接口给出关键路径；任务给出任务类名。
6. 核对图、清单、正文和数量汇总；每个业务动作都必须能追溯到接口、任务、数据变更或事件。
7. 按项目能力运行 Markdown、链接、测试、构建或渲染检查；未执行的检查必须如实报告。

设计必须遵守“低耦合、高内聚”：每个模块、接口和任务只负责单一业务职责，依赖通过清晰契约连接；禁止跨模块直接读写非本模块拥有的数据或把多个业务职责塞进一个设计单元。

## 文档结构

以 [references/detailed-design-template.md](references/detailed-design-template.md) 的轻量模板为起点。需要额外细节时只增加与当前实现有关的行或附录，不扩展整套章节。

- 定义接口、任务、表、事件、编号和追踪关系时，读取 [references/design-inventory-rules.md](references/design-inventory-rules.md)。
- 审查完整性、清晰性和实现就绪度时，读取 [references/design-review-checklist.md](references/design-review-checklist.md)。

推荐顺序：

1. 实现清单
2. 接口/任务主逻辑
3. 数据表关系
4. 关键约束
5. 待确认项与汇总

没有对应内容时删除章节，不用“暂无”或“无”堆满模板。

## 设计单元契约

接口或任务是最小可交付单元。单元标题必须带完整引用和接口路径或任务类名。主逻辑独立成段；公共章节只说明跨单元事实。只有会改变实现的差异才展开，避免“同上”和重复背景。

所有全局引用必须使用“编号 + 对象名称”，格式为 `<类型><序号>-<对象名称>`，例如 `API1-CreateOrder`、`JOB1-SmokeTask`、`DB1-fund_order`、`EVENT1-OrderCreated`、`LOG1-CreateOrderStart`。禁止只引用 `API1` 或 `JOB1`。复制或新增设计单元后，必须重新分配全文全局唯一的引用，并同步更新清单、图、正文引用和汇总数量。

## 写作与交付要求

- 使用短句和明确动词，一个段落只解决一个问题。
- 调整既有逻辑时必须显式高亮改动点：正文、表格和交互步骤中的变更内容使用 Markdown 粗体 `**变更内容**`，只加粗发生变化的文字，不加粗整段或整个章节。
- 流程图中的既有逻辑改动节点使用独立 `changed` 红色语义类，并在节点文字中增加“变更：”；时序图用淡红色 `rect` 包裹受影响消息，并使用 `Note` 或消息文字标明“变更”。颜色只能辅助识别，不能替代文字标识。
- 纯新增逻辑不强制高亮；未调整的既有逻辑保持普通样式。不得把异常红色语义类 `exception` 当作改动标记。
- 首次出现的领域术语给出简短定义；标识符、路径、命令、字段名和协议值保持原文。
- 表格只承载清单、表关系和关键约束；复杂因果关系使用流程图或时序图，图中编号必须与清单一致。
- 默认控制信息量：接口/任务单元正文优先不超过 1 页；每个单元最多一张主流程图、一张主时序图和一张关键约束表，扩展内容按需附录。
- 每个流程图和时序图章节必须包含实际 Mermaid 源码，不得只保留文字说明或占位符；流程图遵循 `$mermaid-flowchart`，时序图遵循 `$mermaid-sequence-diagram`。
- 模板图只用于展示结构。复制后必须按实际业务替换节点、参与者、分支、路径、重试策略和全局引用，不得原样交付。
- 不编造响应时间、吞吐量、数据量、兼容性或告警阈值；缺少依据时标注来源或“待确认”。
- 严格执行 [references/design-inventory-rules.md](references/design-inventory-rules.md)；未落地的类、方法、表或路径标注“拟定”，不能写成现有事实。
- 数据表设计必须解耦：一个 `DB` 编号和一个数据表设计块只能描述一个物理表或集合；涉及多个表时拆成多个独立设计块，跨表关系单独描述。
- 同一处引用同一张表的多个字段时使用 `表名.字段1/字段2`，斜杠后的字段继承表名前缀；不同表的字段必须分别写完整表名。字段定义表仍按一行一个字段描述。
- 每个模块、接口和任务必须说明职责边界、拥有的数据、允许的依赖和禁止的直接依赖；跨模块交互只能通过接口、事件或明确的数据契约完成。
- 日志至少包含 `traceId`/`requestId`、业务主键或任务批次号等链路字段；敏感字段必须脱敏、摘要化或禁止记录。
- 只改设计文档时不修改业务代码；发现实现冲突时报告可验证事实。
- 最终报告修改范围、接口/任务/表/事件/日志数量、性能验证方式和未决问题，不声称未执行的检查已通过。

## 完成检查

- 实现清单完整，全局引用均使用“编号 + 对象名称”、保持全文唯一，并与设计单元数量一致。
- 每个接口/任务设计单元都能独立交给开发和测试阅读，不依赖猜测关键行为。
- 主流程、异常、重试和状态流转有明确入口、出口和责任边界。
- 每个接口和任务均说明输入、处理、输出或状态变化。
- 每张数据表/集合均说明所有权、读写方和表关系；字段、索引、生命周期和迁移仅在新增、变更或影响实现时展开。
- 模块职责边界清楚，核心逻辑集中在所属模块，跨模块依赖数量和方向可解释。
- 日志只覆盖关键业务事件、级别、链路/业务字段和敏感信息处理。
- 性能只记录有依据的规模、目标、瓶颈和验证方式；未知项标为“待确认”。
- 图、表、正文和汇总没有矛盾；假设没有被写成事实。
- 既有逻辑改动在正文、流程图和时序图中采用一致的文字标识与高亮范围，没有漏标或整篇过度高亮。
- 已删除重复背景、空泛口号和与编码无关的内容。
