# 接口压测

只负责接口压测执行和结果整理。执行前确认目标、压测粒度、并发梯度、持续时间、鉴权文件和结果目录；执行后保留原始日志、k6 汇总，并维护三层压测报告。

标准执行模板见 [references/sop-template.md](references/sop-template.md)。每个压测套件都应提供唯一的一键入口，并把环境差异收敛到少数配置项。

## 测试思路

按分层递进组织压测，每轮必须显式声明压测粒度（单接口/混压），默认单接口：

1. **单接口基线轮**：低并发（1~5 VU 或少量 RPS）跑通目标接口，记录空载延迟和错误率作为基线；基线不干净（有失败、抖动大）时，后续轮次不作数。
2. **单接口梯度轮**：默认形态。一次只变并发或吞吐这一个变量，阶梯升档找拐点，每档对比基线判断退化幅度。
3. **浸泡轮（soak，可选）**：中等负载持续 30 分钟以上，观察内存泄漏、连接池耗尽、P95 随时间爬升等慢退化。
4. **混压/链路轮（可选，须显式声明）**：多接口按比例组合模拟真实业务流量，回答"整体链路是否扛得住"；其结果不得当作任何单接口的容量结论，且必须先有对应单接口轮次作参照。

负载模型按目标选择：容量测试优先用开放式模型（`ramping-arrival-rate`/`constant-arrival-rate`，吞吐不随系统变慢而下降）；浸泡可用 `constant-vus`。凡多接口混合运行的轮次，必须按接口设置 tag 或 URL 分组，指标按接口拆分，禁止只看混合总均值。

## 触发边界

- 只有用户明确写出 `$api-load-testing` 时使用。
- 用户只说"执行/启动/重跑接口压测"或"用 k6 做梯度并发测试"但没有指定本技能时，不使用本技能。
- 仅要求解释脚本、审查代码、查看结果、编写普通测试时不使用。
- 未得到明确目标环境和接口时，不自行向生产或外部环境发压测流量。

## 执行流程

1. 阅读目标压测目录的 `README.md`、唯一入口脚本、数据文件和本地测试说明；确认本轮压测粒度和被压接口清单。
2. 优先使用套件唯一入口；只允许修改 `BASE_URL`、`AUTH_FILE`、`DATA_FILE`、`RESULTS_ROOT` 四项配置，梯度、比例、阈值和请求逻辑由脚本管理。
3. 确认目标 URL、请求方法、请求体、鉴权方式、Token 是否过期；严禁在终端输出或报告中展示 Token。
4. 检查 `k6`、`jq`、`node` 等依赖，并确认没有其他同一套件的 k6 进程。
5. 读取脚本内置场景，不在命令行堆叠覆盖参数；不得擅自增加场景、并发限制或数据类别。若套件只有混压场景而用户要单接口结论，先向用户说明并同步拆分脚本方案，不得直接拿混压结果交差；套件缺基线或单接口场景时同样先同步脚本方案，不得跳过基线直接跑梯度。
6. 压测前先说明本轮思路、粒度、档位、总时长、停止条件和结果目录。
7. 入口脚本必须自动创建带日期、时间、环境、场景和粒度标识（接口名或 mixed）的结果目录，不得覆盖历史结果。
8. 使用前台会话运行 k6，持续观察升档、保持、降档、进程退出、EOF、timeout、HTTP 失败和阈值状态；不要重复启动第二个 k6。梯度轮每档保持时间要足够（建议 3~5 分钟以上），浸泡轮关注指标随时间的漂移。
9. 结束后检查退出状态、`summary.json`、完整 `run.log` 和每个 VU 档位指标；中断或鉴权失败的轮次不得当作性能结论。
10. 轮次结束后由技能执行者完成三层报告：当轮 `结果摘要.md` 落盘 → `RESULTS_ROOT/轮次索引.md` 追加一行 → `最新压测报告.md` 更新对应接口章节。`run.sh` 只产出 `run.log` 和 `summary.json`，不负责报告。

## 结果判断

- 明确区分：HTTP 非 2xx、接口设计内 503、网络 EOF/timeout、响应字段错误、字段降级。
- k6 `Rate` 指标必须结合 `passes`、`fails` 和 `rate` 解读，不能只看字段名或单独看 `rate`。
- 记录每个并发档位的请求数、失败率、P95/P99、最大耗时、设计内 503 数量和是否中断；不得用平均耗时下结论。
- 混压轮必须按接口 tag 拆分 P95/P99 和失败率后再解读；脚本拆不出来时写明"本轮无法按接口归因"。
- 拐点判断要给出依据：吞吐不再上升、P95 相对基线成倍恶化或失败率突增的档位。
- 若脚本按比例准备 L1/L2/DB 样本，只能称为"计划比例"；实际 L1、L2、DB 命中率必须以服务日志或正式指标确认，不能由样本计数冒充。
- 发现 Token 过期、目标不可达或全量鉴权失败时，停止把该轮当作容量测试，并单独标记为无效结果。

## 报告要求

使用中文、通俗表述，报告分三层、历史与最新并存：

- 历史明细，一轮一报告一目录：每轮压测对应一个结果目录和一份独立的 `结果摘要.md`；默认一轮只压一个接口，混压轮的多接口仅用"按接口拆分"一张表呈现。
- 历史索引：`RESULTS_ROOT/轮次索引.md`，每轮一行链接加一句结论，只增不改。
- 最新状态：`RESULTS_ROOT/最新压测报告.md`，以接口为章节——每个接口一章，正文为该接口最新一轮"有效"压测的完整摘要，章末附历史轮次索引；混压/链路单独成章，其结论不得写入单接口章节。每轮结束必须同步更新对应章节。

报告结构按 [references/report-template.md](references/report-template.md) 的固定模板填写，至少说明：

- 测试接口、压测粒度（单接口/混压及配比）、环境、Token 状态、梯度和总时长。
- 每档 P95、P99、失败率、设计内 503 和异常类型；混压轮附按接口拆分表。
- 是否出现并发拐点，以及判断依据。
- 有效性结论：有效，或无效并注明原因（中断、鉴权失败、目标不可达）。
- 原始文件的绝对路径：`summary.json`、`run.log`、摘要文件。
- 未观测到的指标要明确写"本轮未采集"，不得推测。

报告遵循精简原则，只保留决策所需信息：

- 表格优先于段落；未采集指标一行带过。
- 六类异常仅数量大于 0 时各占一行，全为 0 合并写"异常：无"。
- 浸泡轮分段只列首段、末段和首个明显恶化段；拐点结论不超过 3 行。
- 篇幅上限：单轮 `结果摘要.md` 正文 ≤50 行，`最新压测报告.md` 每接口章节 ≤30 行。

## 仓库约束

- 结果只放 `perf/k6/<suite>/results/`，不要提交压测结果、Token、本地鉴权文件或临时脚本。
- 只修改用户指定的压测套件；不要删除历史结果和其他套件文件。
- 修改脚本时先补充或更新结构测试，再做本地 `npm test`/`k6 inspect`；执行真实压测前先向用户同步方案。
- 新套件按 [references/suite-scaffold.md](references/suite-scaffold.md) 落地：提供 `config.example.json`、本地配置文件模板、唯一入口（推荐 `run.sh`）、内置场景和数据文件格式；用户不应直接编辑 k6 入口脚本。
- 新套件的 README 必须写明被压接口清单、每个场景的粒度和负载模型；单接口场景与混压场景分开定义、分开执行，不得共用一个场景混出结果。
